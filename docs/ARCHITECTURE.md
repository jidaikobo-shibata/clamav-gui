# コードの責務とOS移植の入口

2026-11-18のリファクタリング後の構成です。画面の操作、保存先、プランID、
サービス名は維持しています。Ubuntu/Linuxに加え、Windows 11 x64の実装を追加しました。

## 画面とアプリケーション

| ファイル | 責務 |
|---|---|
| `clam_gui/__main__.py` | Application、メイン画面、選択・実行状態、画面間の接続と起動/終了 |
| `clam_gui/ui/plans.py` | プラン編集・複製・削除と予定の編集 |
| `clam_gui/ui/preferences.py` | 検査設定、監視・履歴、常駐監視の設定画面 |
| `clam_gui/ui/packages.py` | ClamAVの導入・削除・定義更新と自動更新設定の画面 |
| `clam_gui/ui/history.py` | 選択したプランの履歴・ログと外部メディア履歴 |

画面はApplicationへ組み合わせる小さなクラスに分割しました。
各クラスはApplicationの状態とコールバックを使うため、単独の別アプリではありません。
画面間の状態の所有者は引き続きApplicationです。画面の全面書換えは行っていません。

## OS連携

`clam_gui/platforms.get_backend()` がOS連携の入口です。
GUIは `self.backend` を使い、個別のOSサービスを直接構築しません。
LinuxBackendは既存のAPT・FreshClam・systemd管理を呼び出します。
WindowsBackendはwinget、FreshClam、タスクスケジューラ、Job Object、GIOのフォルダー監視とリムーバブルドライブ列挙を利用します。実装は `clam_gui/platforms/windows*.py` にあります。macOS向けの選択処理は未実装です。
未実装のOSは明示的なエラーを返し、Linuxの管理コマンドへフォールバックしません。

| メソッド | 戻り値・役割 |
|---|---|
| `scheduler(store)` | `apply(key, schedule)` / `remove_profile(key)` を持つ定期実行管理 |
| `packages()` | `package_names` / `status()` / `preview(action)` / `execute(plan)` を持つ導入管理 |
| `can_update(installed)` | 導入状態から定義更新の準備があるか判断 |
| `updater()` | 定義更新処理。既存の中断・進捗・復元の引数を維持 |
| `auto_update()` | 定義自動更新の `status()` / `set_enabled()` |
| `background(store)` | `path` / `supported()` / `apply(enable)` を持つ常駐起動管理 |
| `observers(engine)` | ファイル・メディアのイベント取得。既存のconfigure/close等の意味を維持 |
| `lock(path)` | `acquire()` が即時にboolを返すプロセス間ロック、`close()` で解放。`file` は取得中かの確認に利用 |
| `spawn_scanner(command, lock=..., **kwargs)` | 親終了時に検査を停止し、終了まではロックを保持する子プロセス起動。wait/terminate/killを持つプロセスを返す |
| `process_identity(pid)` | 生存個体の識別子、死亡確認済みなら空文字、確認不能ならNone |
| `notify(title, body, urgency)` | ウィンドウを持たない処理からの通知配送。失敗時は例外 |
| `definition_label()` / `definition_status()` | 各OSの定義保存先に対応する日時・鮮度の表示 |
| `install_stop_handlers(callback)` | 常駐プロセスの停止要求をメインループへ接続 |

`fcntl` はLinuxのロック実装で必要になったときだけ読み込みます。
`/proc` のプロセス識別とnotify-sendもLinux側へ移しました。
これはOS移植の入口をそろえる変更です。Windows/macOSの保存先・引数・配布・通知等を
実装済みにするものではありません。OSごとの実機確認は引き続き必要です。
GTKアプリからの通知はGio.Notificationを利用し、内容の判断だけを常駐側と共有します。

## 検査結果

`clam_gui/results.py` に `ResultKind`、`Assessment`、`ScanStatus` を置いています。
区分はclean / detected / warning / incomplete / cancelledで、検出の有無は別属性です。
検出を伴う不完了・中止も表現できます。

- 新しい検査結果はClamAVの出力と終了コードから区分を作り、表示文で再判定しません。
- `assess(status, output)` から区分・検出・正常・完了を確認します。
- `ScanStatus` は既存の `(status, output)` APIを保つための文字列互換アダプターです。説明の追記でメタデータを維持します。判断前にf-stringやstr変換で単なる文字列にしないでください。
- SQLiteへは表示文とは別に `result_kind` と既存の `detected` を保存します。
- 古い行の `result_kind` はNULLのままです。既存の行を一括書換え・削除せず、互換処理で日本語の旧表示から判定します。
- `core.summarize` / `core.has_detection` は従来の呼び出し元のため再公開しています。

通知・履歴整理・自動検査の重複抑制には、共通の判定を使用します。
不完了の検査は、検出があっても完了済みキャッシュへ登録しません。

## 監視・失敗処理・設定

- `automation.py` は待機キューと自動検査の実行、`monitor.py` は画面なしのメインループと再開確認を担当します。
- `notifications.AutomaticNotices` が、正常結果の20秒集約と異常の即時通知の方針を共通化します。配送はGUI/常駐/OSのアダプターに任せます。
- `jobs.execute_scan` は、検査と失敗報告を同じ結果形式へまとめます。自動処理で再試行する競合例外は呼び出し元へ返します。
- 自動検査のスレッド起動失敗では実行中状態を解除して履歴・完了通知へ進みます。
- `settings.Preferences` にJSON設定の読み書きを集約し、複数設定と履歴整理は呼び出し元のSQLiteトランザクションで確定できます。
- 画面の状態更新では、予定・監視設定・常駐状態を更新1回につきまとめて取得し、プランごとの再読込を抑えています。

## 検証

既存の共通・OS実装のテストを維持し、`tests/test_refactoring.py` で
表示文と判定の独立、旧結果の互換、保存と履歴整理、通知集約、OS境界、設定の原子性、失敗復帰を検証します。
GUIの操作は分離Wayland、常駐は一時データと模擬検査の独立プロセスで確認します。
実端末への導入・削除、サービス/予定の再登録、実ファイル検査はリファクタリングの検証では実行しません。

## 実行枠と待機

`execution.py` が full / event の実行枠、共通ロックのパス、競合・重複・上限の例外を定義します。
全体検査は従来のロックを維持し、監視ファイルとメディアは別のロックを使用します。
`scan(..., wait=True)` はSQLiteの受付順で同じ枠の先行処理とロック解放を待ちます。
`wait=False` は既存APIの即時取得を維持し、自動監視側が競合を再キューイングします。

`scan_runs` の6列は維持し、`scan_run_details` にwaiting/runningとlaneを保存します。
旧プロセスの詳細なしの記録はfull/runningとして扱います。登録はBEGIN IMMEDIATEで直列化し、
同じprofile_id/laneを重複登録しません。上限32件には実行中も含みます。
待機順の先行レコードはPID再利用を含め生存確認し、死んだ所有者の記録は待機を妨げません。

待機はキャンセル要求と予定の有効性を確認しながら進めます。
中止した待機はcancelledとして履歴へ残し、重複統合は失敗履歴を作りません。
待機終了後に対象・最新の検査オプションを確認し、実行開始時刻を更新します。
定期通知の所要時間は待機を除きます。GUIは手動依頼ごとの取消イベントを持ちます。

`tests/test_execution.py` では一時データと模擬スキャナーを別プロセスで動かし、
2枠の並行性、同じ枠の順番、重複・取消・予定無効化、上限、旧記録互換を確認します。

## 検査プロセス・変更検知・通知の契約

- Linuxの検査起動は専用のexecヘルパーを使います。ヘルパーも配布対象に含めます。別スレッドのあるGUIでpreexec_fnを使わず、設定に失敗した場合は未保護の検査を開始しません。通常ユーザーの権限で動作します。
- 他OSのspawn_scanner実装も、所有者終了時の子停止と、子終了までの実行枠保持を保証してください。Linuxヘルパーを他OSで呼びません。
- 変更イベントは検査済みキャッシュを無効化します。再開比較の形式を更新した際は比較元を作り直します。各OSで更新日時以外の変更指標も確認してください。検査中に届いた再変更は次の検査へ残します。
- notification_outboxは常駐側の配送を担当します。notifyアダプターはOS APIへの受け渡し失敗を例外で報告してください。失敗を握り潰すと配信済みと誤認します。
- 配送は1ワーカー、個別256件＋2種類の件数要約で保存量を抑えます。配信claimの期限は60秒で、異常終了した配送を引き継げます。受理後の記録確定前に異常終了した場合は再表示を許容します。
- 再試行は5秒から最大300秒です。GUIのGio.Notificationと定期検査CLIの通知配送は従来の経路を維持します。
- 子プロセス保護の参考：[Linuxの親終了シグナル](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html)、[Pythonのsubprocess](https://docs.python.org/3/library/subprocess.html)。

## 履歴・監視の処理量

- 履歴一覧はprofile_idと旧targetの索引から最大100件の見出しだけを取得します。本文は選択した1件を別途取得します。旧記録の完了日時・検出判定が必要な場合も本文を1件ずつ処理し、本文一覧を保持しません。
- UIの履歴読込みはLatestReaderの1ワーカーで行い、待機要求とUI配送をそれぞれ1件に集約します。プランや日時を素早く切り替えた場合は旧要求の結果を破棄します。ウィンドウ終了後は配送しません。
- GIOのディレクトリ列挙はscandirを保持して再開し、1回128ステップまたは約8msでメインループへ制御を戻します。OSの単一I/O呼出しの遅延自体は打ち切れません。変更・停止時は列挙ハンドルを閉じ、準備中の列挙が終わるまで比較元を完了扱いにしません。リンク・除外・範囲の検証と既存の件数上限は維持します。
- retention_infoは日時・重要度・バイト数、retention_totalsは件数と容量を保存します。scansの挿入・更新・削除トリガーで差分を追跡し、旧版による書込みも次の整理で反映します。通常の保存では判定済みの結果を直接登録し、全履歴をPythonへ読みません。
- 古い記録は初回の整理有効化時に512件ずつ分類します。初回だけ既存件数に比例した処理があります。設定無効時に履歴を削除せず、期間・通常結果優先の容量/件数上限は従来と同じです。履歴本文の書換えやVACUUMは実施しません。
- 常駐の制御要求・通知キュー確認は約1秒単位、生存確認は状態変化時と約3秒単位です。有効期限8秒より短い間隔を維持します。監視準備が完了した比較元の再保存も省略します。通知配送は独立ワーカーと永続キューを維持します。
- tests/test_performance.pyで本文のメモリ保持、旧履歴互換、非同期要求の集約、履歴差分整理と旧版書込み、監視準備の分割と中断、生存確認と制御要求を検証します。GUI検証は全確認を終えた子プロセスの完了印も確認します。

## 常駐監視の負荷抑制

- 監視準備のqueuedはモニター数とは独立に最大limit件（初期値1024）へ制限します。列挙中のフォルダーも含め、拒否はプランごとに一度報告。範囲変更時は状態を初期化し、終了時は待ち行列も解放します。除外フォルダーを列挙待ちへ入れません。既存のmonitor上限も維持します。
- WatchQueue.takeはquiet期間内と別プランの項目をファイルシステムへ問い合わせません。期限を迎えた候補を1tick最大64件確認し、従来どおり最大50ファイルを検査します。取得時に範囲・リンク・署名を確認し、変更を見つけたらquiet期間を延長します。検査本体でも再検証します。
- Automationは開始間隔15秒、完了後休止2秒を適用します。待機中も既存の上限1000件のキューで変更を集約し、状態に待機理由を表示します。競合時も同じ間隔で再試行し、対象を捨てません。自動メディア検査にも適用し、手動/定期の全体検査や2枠の構成は変更しません。clamdの共有・設定変更は行いません。
- Linuxのscanner_guardは所有者保護の設定後、子自身のniceを最低10へ下げます（既により低優先度なら維持）。既存ioniceが利用可能なら子のI/Oクラスをidleへ変更。未導入・拒否・タイムアウトはNOTEとして記録し、通常優先度で検査を続行します。外部ライブラリや自動パッケージ導入は追加しません。
- 再登録する常駐unitはCPUWeight/IOWeight=20、監視本体のI/Oはbest-effort/7です。制御用DBのI/Oをidleにせず、検査子だけidleにします。既存unitは自動変更せず、環境設定の再起動/有効化で再生成します。
- 優先度は帯域・CPU・メモリの絶対上限ではありません。大きな検査のRAM負荷、OSのI/Oスケジューラ差、全体検査との重複は残ります。根拠のないメモリ上限による強制終了は追加していません。Windows/macOS担当は各OSの同等の低優先度機構を実装してください。
- tests/test_monitor_load.pyで期限前のI/Oゼロ、期限後の確認上限、イベント欠落時の再確認、フォルダー待ち上限・不完了記録・比較元の未完了維持、起動間隔・休止・競合再試行、優先度の実子適用・失敗継続を確認します。壁時計を使うGUI検証だけ起動間隔を短縮し、本番間隔は模擬時計で検証します。
