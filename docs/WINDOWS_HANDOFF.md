# Windows担当Codexへの依頼

Windows担当者のCodexへ、この文書を読んで実装を進めるよう依頼してください。
目的は、PCに詳しくない社員も、コマンドを入力せずClamAVの準備・更新・検査を行えることです。
計画の提示だけで終わらず、動く小さな単位で実装・検証・記録を進めてください。
この文書は2026-11-18時点の公開用コードを基にしています。Windows実機では未検証です。

## 1. 作業の開始

- 対象は https://github.com/jidaikobo-shibata/clamav-gui です。Ubuntuの個別運用を含む別リポジトリは対象にしません。
- 担当者から共有された最新のmainと作業ツリーを確認し、Windows対応ブランチを作ってください。未コミット変更を上書きしません。
- README.md、この文書、`.codex/work-log.md`、配置されていればAGENTS.mdを読んでください。
- CONTRIBUTING.mdの前半はmacOS担当者向けです。製品の共通仕様とコード案内は参考にし、Homebrew・launchdの指示をWindowsに適用しません。
- macOS担当者も開発しています。共通バックエンドの設計と変更予定を担当者間で共有し、大きな共通化やGUIの全面書換えを独断で進めないでください。
- Windowsの版・CPU、Python・GTK 4・PyGObject、ClamAV、既存の更新処理、利用できるパッケージ管理ツールを読み取り確認してください。
- 実装前に、起動を妨げる箇所と最初の作業範囲を簡潔に報告してください。回答待ちの間も独立して進められる作業は進めてください。
- WSL上で動作しただけではWindows対応の完了にしません。Windowsの通常ユーザーのデスクトップで使えることが目標です。

## 2. 維持する製品方針

- ClamAV本体・定義ファイルはGUIに同梱せず、端末にあるものを使います。GUI導入後に、GUIからClamAVを準備する流れです。
- ClamAVの導入・削除、定義の取得・手動更新・自動更新は重要な機能です。開発者による事前インストールだけで製品の導入機能を完了としません。
- 既存のPython 3.10以降・GTK 4・PyGObjectをまず使います。別GUIへの全面移行は先に担当者へ相談してください。
- 検査は `clamscan` 方式を維持し、`clamd` の導入・常時起動を必須にしません。
- ファイルの自動削除・隔離は行いません。通常ユーザーで検査し、読取権限不足・サイズ上限・未導入・開始失敗の理由を表示して履歴へ残します。
- 個別のメールアドオンとの連携は製品仕様にしません。mbox等で複数メールが一つの保存ファイルになっている場合の注意表示は維持します。
- ClamAV本体の更新、定義ファイルの更新、GUI自身の更新は別です。本体の独自自動更新とGUIの自動更新は今回の必須範囲ではありません。
- ライセンスはWTFPL v2です。新規依存・ランタイム配布は必要性・保守性・ライセンスを説明してください。ClamAVを同梱しない方針と、GUI用ランタイムの配布設計は区別します。

## 3. 現在の機能と意味

| 項目 | 維持する動作 |
|---|---|
| 検査プラン | 名前・基本フォルダー1つ・除外フォルダー/ファイル・実行方法を管理。左ペインで選んだプランの日時とログを右側に表示 |
| プラン操作 | 追加・編集・複製・削除・今すぐ検査・中止。複製の自動実行は無効、削除しても実ファイルと過去の検査履歴は残す |
| 定期検査 | 毎日・毎週・毎月1〜28日・毎時・1〜1440分間隔。間隔は初回が登録からn分後、その後は前回完了からn分後 |
| 定期実行の無効化 | 未来の起動だけを止め、実行中の検査は続ける。中止操作とは別 |
| 検査設定 | ClamAVの対応オプションとサイズ上限。標準値は実際のClamAVから確認し、非対応項目を黙って成功扱いしない |
| 通知・ログ | 成功・検出・不完了を記録して通知。検出日時を太字。定義の最終書換日時と、更新確認日時を区別 |
| フォルダー監視 | 追加・変更が3秒落ち着いてから最大50ファイルを集約。除外・子フォルダー設定・一時ダウンロード名・取りこぼし警告を扱う |
| 外部メディア | 環境設定でオンにすると専用プランを表示。読み取り可能なリムーバブルメディアを検査し、途中の取り外しは不完了。オフでも履歴を閲覧可能 |
| 常駐監視 | 初期状態は無効。確認して有効にするとログイン中はGUIを閉じても監視・通知。GUIと常駐プロセスの二重監視を防ぐ |
| 再開確認 | 初回は比較元を作り、全ファイルは検査しない。常駐の再起動・復帰時に追加変更を確認。停止中に消えたファイルやメディアは回復できない |
| 履歴の上限 | 初期状態は無効。有効化・有効中の条件変更時に削除条件を確認。期間・論理容量・件数で整理し、上限次第では検出・不完了も削除される |

定期的な全体検査は監視の補完として残します。ファイルの利用を遮断するリアルタイム保護ではありません。
常駐監視の無効化では、そのプロセスの自動検査は中止します。GUIが開いていればGUI側の監視へ戻ります。
これは定期実行スイッチの意味とは異なります。電源オフ・スリープ・ログアウト中の検査は保証しません。

## 4. 移植の入口とOS依存箇所

**現状では `core.py` と `background.py` のトップレベルに `fcntl` のimportがあります。**
Windowsで画面を開く前に失敗し得ます。UIの小修正だけで移植できるとは扱わないでください。

| ファイル | Windows対応で確認する点 |
|---|---|
| `clam_gui/__main__.py` | GUIからUbuntu実装への接続。起動案内、設定、状態表示、操作の確認を維持してOS別実装へ接続 |
| `clam_gui/core.py` | SQLite・プラン・検査。`fcntl`、ホーム配下の共通ロック、固定引数、除外の正規表現と `/` 区切り、UTF-8前提の出力解析 |
| `clam_gui/options.py` | 実際の `clamscan.exe --help` に基づく対応と初期値の確認。固定引数も別途確認 |
| `clam_gui/runtime.py` | Linuxの `/proc`・boot ID・開始時刻によるプロセス識別。PIDの存在だけの確認に置き換えない |
| `clam_gui/packages.py` | APT・dpkg・pkexec・cgroup。Windowsで読み込み/実行すべき箇所を分離 |
| `clam_gui/definitions.py`, `notifications.py` | `/var/lib/clamav` 等の固定パス、FreshClamのsystemd/journal、通知文の共通部分 |
| `clam_gui/schedule.py`, `scripts/run_scheduled.py` | systemd・固定Python・notify-sendをWindows方式へ置き換える |
| `clam_gui/automation.py` | 待機・重複抑制・メディアの生存確認。Windowsの大小文字・再解析ポイント・ボリューム識別との整合を確認 |
| `clam_gui/gio_watch.py` | GIOのフォルダー/メディア検知。Windowsの実機で使える範囲を調べ、不足をアダプターで補う |
| `clam_gui/background.py` | systemd管理と `fcntl` の監視所有権。SQLiteの状態・要求共有は共用を検討 |
| `clam_gui/monitor.py`, `scripts/run_monitor.py` | GTKなしの監視プロセス。GLibのUnixシグナル処理・notify-send・停止/復帰検知を移植 |
| `clam_gui/retention.py` | 履歴整理。データ互換と確認の意味を維持し、Windows移植を理由に既存履歴を削除しない |
| `scripts/launch_gui.py`, `install_launcher.py` | LinuxのDesktop Entry。Windowsの起動経路と依存解決は別途必要 |
| `scripts/smoke_gui.py`, `smoke_monitor.py` | Ubuntuの分離検証。Windows用の隔離した検証を追加し、Linux専用手順をWindowsへ強制しない |

OS別の実行ファイル・保存先・ロック・プロセス識別・導入・更新・予定・通知・監視を分離してください。
ただし抽象化だけを先に大量に作らず、段階ごとに動く最小の構成を選びます。
Ubuntuの保存先・アプリID・systemdの名前・共有ロックの意味と、SQLiteの既存ID/履歴を維持してください。

## 5. Windowsでの実装方針

### 起動環境・保存先・配布

- Python/GI/GTKの組合せを先に実機確認します。[PyGObjectの公式手順](https://pygobject.gnome.org/getting_started.html#windows)はMSYS2 UCRT64での開発環境を案内しています。これを開発の出発点にし、Windows標準Pythonへの単純なpip導入だけで動くと仮定しません。
- MSYS2の開発用シェルからの起動と、一般利用者のスタートメニュー/ショートカットからの起動を分けて確認します。TerminalのPATH・カレントディレクトリ・シェル初期化に依存させません。
- 安定したPython/GUIランタイム起動経路を決め、不要なコンソールを出さず、起動失敗は確認できるようにします。ランタイムを配布する方式は依存とライセンスを説明してください。
- 履歴・設定・ログ・定義等の保存先をWindowsの既知フォルダーと権限に合わせて決めます。Program Filesの書換えを通常ユーザーに要求しません。
- 空白・日本語のユーザー名、ドライブ文字、大小文字、バックスラッシュ、UNC、長いパス、ジャンクション/再解析ポイントを扱います。未対応範囲は明記します。
- `chmod(0o600)` を呼んだだけでWindowsのACLが保護されたと判断せず、SQLiteと状態ファイルの実際のアクセス範囲を確認します。

### ClamAVの導入・削除

- [ClamAVの公式導入資料](https://docs.clamav.net/manual/Installing.html)と[公式配布元](https://www.clamav.net/downloads)を調べ、まず公式Windows MSIを候補として選定します。CPU・対象OS・更新経路を実機で確認します。
- winget等を使う場合は、その環境での有無、パッケージID・配布元・所有関係を確認します。パッケージがあると未確認のまま固定せず、winget自体の導入を隠れた前提にしません。
- 既存のMSI/ZIP/別管理ツールによる導入を検出し、削除対象の所有元を判定します。不明なものを強制削除しません。
- ダウンロード元・版・CPU・変更範囲を説明し、利用できる公式の検証情報や署名を確認します。URLやバージョンの直書きだけで更新可能な導入機能としません。
- UACが必要な操作はその部分だけに限定し、GUI・検査・監視全体を管理者権限にしません。ユーザーが認証を取り消しても復帰できるようにします。
- 昇格先にユーザーが書換え可能な任意スクリプトや引数を渡して実行する設計を避けます。管理者パスワードをアプリに入力・保存させません。
- 検査/更新中の削除を防ぎます。削除前に本体・サービス・設定・定義の保持範囲を説明し、再導入後も検査プラン・履歴を維持します。
- Defenderや他社製の保護を無効化したり、例外を自動登録したりしません。

### 定義の取得・更新

- `freshclam.exe`、設定ファイル、定義ディレクトリを検出し、GUIの日時表示・鮮度判定・検査・更新で同じ保存先を使います。PATHだけで起動できたことを成功としません。
- サンプル設定の準備が必要か調べ、既存設定は上書きしません。定義初回取得までGUIから進められるようにします。
- [ClamAV公式のサービス説明](https://docs.clamav.net/manual/Usage/Services.html)を読み、対象版のFreshClamのサービス対応を確認します。`clamd` の起動を定義の自動更新と取り違えません。
- 既存の更新管理があれば尊重します。なければユーザーのログオンタスク/更新プロセス等を候補にし、Windowsサービスが必須かを先に検討します。
- 自動更新の有効/無効と稼働状態を区別し、GUI終了後も選んだ方式で更新できることを確認します。手動更新のために一時起動した処理は元の状態へ戻します。
- 更新の二重起動、過去ログの成功との混同、HTTP制限時の連続再試行を防ぎます。設定やサービスの変更範囲を確認してから実行します。

### 定期実行・常駐監視

- 定期実行とログイン時の常駐起動は、まず現在のユーザーのタスクスケジューラを候補とします。[タスクのセキュリティコンテキスト](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks)に従い、通常ユーザー・対話ログオン中の実行を基本にしてください。
- 最初からSYSTEMや「最上位の特権」、ログオンパスワードの保存を前提にしません。ログアウト中の動作まで保証しないでください。
- アプリ所有の名前空間とタスクだけを登録・更新・解除します。既存タスクとの衝突を検出し、登録失敗時に設定を復元します。
- タスクの固定周期と「検査完了からn分後」は同じではありません。後者を維持する仕組みを用意し、変更が必要なら先に相談します。
- 常駐はウィンドウなしで動かし、GUIと検査プラン・履歴・実行状態・中止要求を共有します。GUIを開き直しても二重監視・二重検査にならないことが必要です。
- 監視所有権と検査実行のロックは別です。両方ともWindowsでプロセス間排他し、プロセス終了で安全に解放される仕組みにします。
- PID再利用を考慮した生存確認を用意し、記録のPIDへ無条件に終了命令を送りません。所有プロセスが中止要求を読み、自分の子プロセスを止めます。
- フォルダー監視は初期列挙・大量変更・一時ファイル・移動・イベント欠落・復帰・監視上限を扱います。再解析ポイントを辿って範囲外を検査しません。
- 外部メディアは[Windowsのデバイス管理](https://learn.microsoft.com/en-us/windows/win32/devio/device-management)等を確認し、挿入と読み取り可能になった時点を区別します。ドライブ文字だけで同じメディアだと判断しません。
- USBで接続されているだけの固定ディスク、仮想/ネットワークドライブ、空の光学ドライブの扱いを明示し、すべてのドライブを無条件に検査しません。取り外し・再接続・同じ文字の再利用を検証します。

### 通知・操作性

- 成功・検出・不完了をWindowsの通知で伝えます。正常な自動検査は集約し、検出・不完了はすぐ通知します。
- [Windowsのアプリ通知資料](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/)を確認して、配布方式・アプリ識別・通知設定に合う方法を選びます。Pythonの開発シェルで表示できただけで配布可能としません。
- GUI終了中、ログオン起動した監視プロセス、定期検査CLIからの通知を実機で確認します。通知できなくても履歴を保存し、原因を確認できるようにします。
- ファイル名や通知文をPowerShell等のコードへ文字列連結で埋め込まず、引数配列・安全なデータ受け渡しを使います。文字コードとWindowsの引数処理を検証します。
- GNOME HIGを参考にした現行の分かりやすい構成を維持しつつ、Windowsのキー操作・フォーカス・ダイアログの親子関係・拡大表示・読み上げも確認します。

## 6. 実装する順序

1. WindowsネイティブのGUI起動と、import時のLinux依存を分離する。
2. 導入済みClamAVによる手動検査、除外・オプション・サイズ上限、ログ・状態・中止を動かす。
3. GUIからの導入・削除・初回定義取得・手動/自動更新を実装する。
4. タスクスケジューラによる定期検査と、GUIを閉じた状態での通知を実装する。
5. フォルダー監視・外部メディア検査・ログオン常駐・再開確認・履歴整理を接続する。
6. コマンドを使わない起動と、別のWindows端末で再現できる導入手順を整える。

各段階で動作範囲と未対応事項を報告・記録してください。未実装機能は動くように見せず、理由を表示します。
macOS担当者と共通部分を分担し、既存のUbuntu実装を壊す大変更は小さく分けてください。

## 7. 検証・完了条件

共通テストの入口は次です。実際のPython名は使用する環境に合わせてください。

```bash
python -m unittest discover -s tests -v
```

- 引き継ぎ元のUbuntu公開用コードは124件のテスト、分離WaylandのGUI検証、ヘッドレス監視の検証を通過しています。Windowsでの成功を意味しません。
- OS固有の実機テストと共通/模擬テストを分けます。Windows移植を理由に共通テスト全体をスキップしません。Ubuntuの回帰確認はUbuntu担当者へ依頼します。
- 実検査は一時フォルダーの無害なデータから開始します。実メール・業務資料・鍵は使いません。検出/警告/未完了はまず模擬出力で検証します。
- 日本語・空白・記号のあるパス、除外、サイズ超過、未導入、権限不足、競合、中止、子プロセス残留、PID再利用、古い定義を確認します。
- 導入→初回定義取得→検査→削除→再導入の実機確認を行い、設定・履歴の保持とUAC取消/失敗復旧を確認します。
- 短周期の定期発火、GUI終了中、GUI再起動後の状態と中止、ログオフ/ログオン、スリープ復帰、通知無効時の記録を確認します。
- フォルダー監視とメディア検査は、大量変更・部分ダウンロード・取り外し・再接続・二重起動防止と、履歴整理の確認取消を検証します。
- 生成したXMLや引数の検査だけで実機機能の完了としません。実機なしで進めた範囲は未検証と明記します。
- テストのデータディレクトリ・タスク名・設定を分離し、後片付けは今回作成したものに限定します。普段の設定を使わないでください。
- 実画面にウィンドウを表示・入力する前には担当者へ知らせてください。

## 8. 承認・記録・Git

- OSへの導入/削除、UAC、サービス/タスク/自動起動・権限変更、既存の人手の記録の上書き/削除、外部送信は、対象と影響を示して担当者の了承を得てから実行します。同じ範囲で承認済みなら再確認しません。
- プロジェクト内の実装・模擬テスト・一時ファイルでの検証は、通常の開発作業として進めてください。
- 判断・変更理由・検証・未完了事項・次の作業は `.codex/work-log.md` に記録します。
- 実ユーザー名、個人用パス、検査ログ、SQLite、トークン、証明書の秘密鍵、署名情報をコミットしません。必要な個別記録は除外/追跡状態を確認した `.codex-private/` に置きます。
- 意味のある単位で今回の変更だけをコミットします。push・PR公開・リリース・署名サービスへの送信は別途指示を受けてください。
- 完了報告には、実機確認した機能、未対応/未検証、依存とライセンス、セットアップ、復元方法、Ubuntuへ引き継ぐ回帰確認を含めてください。
